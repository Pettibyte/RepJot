# Static data contracts: `exercises.json` and `workouts.json`

Status legend and source abbreviations: see `docs/contracts/README.md` and `families-and-files.md`. Owner abbreviations: sem = semantic validator (`src/validation/semantic-validator.ts`), schema = JSON Schema gate, compat = prior-production comparison build gate, curation = curated build pipeline. The first owner listed is primary; gates after `supporting:` are auxiliary and never co-own the rule.

## 1. Exercise directory fields

| ID | Contract | Source | Owner | Positive case | Negative case | Status |
| --- | --- | --- | --- | --- | --- | --- |
| EX-01 | Every exercise and equipment entry has a stable non-empty `id`; published IDs are never deleted or reused (invariants 23, 24). | Req 6.1, 6.3 (supporting: spec §8 inv 23-24; exercises schema) | compat (supporting: sem) | Prior ID present with corrected label. | Prior ID absent, or ID reappearing with a different entity/role: build fails (Req 6.14). | RESOLVED |
| EX-02 | `name` is non-empty; `instructions` is an ordered string array that may be empty and is the only free-text field on an exercise. | spec §2 (supporting: exercises schema) | schema (supporting: curation) | Empty instructions array valid. | A `description` or other free-form field: schema rejects (`additionalProperties: false`). | RESOLVED |
| EX-03 | One optional discriminated `icon` on exercises and equipment: `material_symbol` with a name, or `local_svg` with a bundle-relative path. Remote URLs, data URLs, and inline SVG source are forbidden; local paths must be same-origin, non-traversing, and end in `.svg`. Build sanitizes bundled SVGs; runtime uses `<img>` only. | Req 9.3, 8.6 (supporting: spec §1 Icon; Arch §15 Untrusted content, ADR-014; exercises schema `icon` pattern) | curation build SVG gate (Phase 7/81) (supporting: schema) | `{ "type": "local_svg", "path": "icons/exercises/back-squat.svg" }`. | `https://…`, `data:image/svg+xml,…`, `/abs.svg`, `../x.svg`, missing file, script or external reference inside the SVG. | RESOLVED |
| EX-04 | `equipmentIds` is a unique array of retained equipment IDs; empty means no equipment (invariant 1). | spec §2, §8 inv 1 (supporting: Req 9.4) | sem | `[]` valid; each ID resolves. | Unknown `equipmentId`; duplicate entry (schema `uniqueItems`). | RESOLVED |
| EX-05 | `force` (`push`, `pull`, `static`, null) and `mechanic` (`compound`, `isolation`, null) are separate nullable enums; `category` follows the free-exercise-db 7-value enum; `movementPattern` is the REP JOT 13-value enum; they must not be merged into one modality field. | Req 9.6 (supporting: spec §2 Classification Enums; exercises schema) | schema | Explicit `null` force or mechanic accepted. | Any value outside the enums; a combined modality field (schema rejects unknown properties). | RESOLVED |
| EX-06 | `primaryMuscles` is a non-empty unique subset of the 17-value free-exercise-db muscle enum; `secondaryMuscles` is a unique subset that may be empty. The source muscle vocabulary is retained unchanged (Req 13.3). | Req 9.5, 13.3 (supporting: spec §2 Muscle; exercises schema `muscle`) | schema (supporting: curation) | All 17 values usable across the directory. | Any invented muscle value; duplicate within one array. | RESOLVED |
| EX-07 | `laterality` is `bilateral` or `unilateral`, describing normal execution only. | spec §2 Laterality (supporting: Req 9.6) | schema | Both values. | Anything else. | RESOLVED |
| EX-08 | `measurements` is a non-empty unique set of dimension entries using exactly the controlled dimension/unit table: `reps/rep`; `weight`, `addedWeight`, `assistedWeight` with `lb`, `kg`; `distance` with `m`, `km`, `ft`, `mi`; `duration` with `second`, `minute`; `calories/kcal`. Each listed unit must be compatible with its dimension. | Req 9.7 (supporting: spec §2 Measurements and Units; exercises schema `measurementSupport` oneOf) | schema (supporting: sem for result values, inv 7-8) | `{"dimension":"weight","compatibleUnits":["kg","lb"]}`. | `{"dimension":"reps","compatibleUnits":["kg"]}`, unknown dimension, duplicate dimension entry. | RESOLVED |
| EX-09 | `loadSemantics` (`total`, `per_implement`, `added`, `assisted`) is conditionally required when a load dimension exists in `measurements`: `weight` → `total` or `per_implement`; `addedWeight` → `added`; `assistedWeight` → `assisted`. The base property also syntactically permits an enum-valued `loadSemantics` on an exercise with no load dimension (e.g., reps-only). Two different load dimensions in one exercise activate two intersecting conditionals whose permitted value sets disagree; no `loadSemantics` value satisfies both, so the document fails schema validation. | Req 9.8 (supporting: spec §2 Load semantics; exercises schema conditional `allOf`) | schema | Squat with `weight` + `loadSemantics: "total"`; reps-only exercise without `loadSemantics`. | `weight` without `loadSemantics`; `addedWeight` with `total`; `measurements` containing both `weight` and `addedWeight` (intersecting conditionals, no satisfying value). | RESOLVED |
| EX-10 | `deprecated` is an optional boolean. A deprecated exercise stays resolvable for history, cannot appear in a new workout or new node, and remains in the bundle (invariants 24; Req 6.5). | Req 6.5, 9.9 (supporting: spec §1 Stable IDs and Deprecation; exercises schema) | sem (supporting: compat) | Deprecated exercise still referenced by a retained workout node and by historical results. | New workout node referencing a deprecated exercise: build fails (spec §1 "A node added to an existing workout is new and cannot reference a deprecated exercise"). | RESOLVED |
| EX-11 | Within one dimension, `compatibleUnits` lists metric units before imperial units (`kg` before `lb`; `m` or `km` before `ft` or `mi`). Single-unit dimensions keep their only unit. The first entry is therefore the deterministic default when no preference exists; no separate default field exists. | spec §4 ("Static data lists metric units before imperial units") (supporting: Arch §13 (unit defaults); Req 12.2 context) | sem (supporting: curation) | `["kg","lb"]`, `["m","km","ft","mi"]` valid orderings; `["rep"]` single unit. | `["lb","kg"]`, `["ft","m"]`: semantic validation fails the static document. Fixture: `tests/fixtures/contract-acceptance/exercises.min.json` (interleaved metric/imperial dimensions across exercises). | RESOLVED |
| EX-12 | The exercise directory never selects a user's preferred unit; `preferences.json` owns that selection. | spec §2 Measurements and Units | sem | Same exercise used by default unit on one account and mapped unit on another. | Any preference read inside static validation. | RESOLVED |

## 2. Workout structure fields

| ID | Contract | Source | Owner | Positive case | Negative case | Status |
| --- | --- | --- | --- | --- | --- | --- |
| WK-01 | A workout has a stable `id`, non-empty `name`, optional author `notes`, a required `root` container, and optional `deprecated`. Deprecated workouts stay resolvable for history, are hidden from the chooser, and cannot start new sessions (Req 6.12). | Req 6.12 (supporting: spec §3 Workout; workouts schema) | sem (supporting: schema) | Deprecated workout still resolves historical session paths. | Starting a session from a deprecated workout; showing it in Choose Workout. | RESOLVED |
| WK-02 | Each node ID is unique within its workout. The same node ID may appear in different workouts; every cross-workout identity uses the composite key `workoutId + "\u0000" + nodeId`, never a bare `nodeId`. | spec §3 ("Each node ID is unique within its workout") (supporting: storage §In-memory read model `nodeKey`; postmortem hidden case (repeated node IDs)) | sem (supporting: index builder) | Two workouts both containing node ID `set-1` validate; lookups never collide. Fixture: `workouts.scenario.json`. | Duplicate node ID inside one workout: semantic failure. Any index or key built from bare `nodeId`. | RESOLVED |
| WK-03 | Published workout nodes keep their parent, type, exercise reference, container strategy, scoring contract, and previously supported units; they cannot move to a different parent because result paths embed ancestry (Req 6.4). New nodes may be added to existing workouts and may not reference deprecated exercises. | Req 6.1-6.4, 6.15 (supporting: spec §1; versioning §Static bundle compatibility) | compat (supporting: sem) | Node added under an existing parent in a later bundle. | Parent or type change for a published node: build fails (Req 6.14-6.15). Fixture pair: `workouts.scenario.json` vs `workouts.later-addition.json`. | RESOLVED |
| WK-04 | Container strategies are exactly `sequence`, `rounds`, `amrap`, `emom`, `complex` with their fixed `strategyConfig` shapes: sequence `{}`; rounds `{rounds ≥ 1}`; amrap `{duration > 0}`; emom `{cycles ≥ 1, interval > 0}`; complex `{cycles ≥ 1}`. EMOM uses `cycles` and `interval`, never `rounds` (Req 10.9). | Req 10.6-10.9 (supporting: spec §3 Container Node; workouts schema per-strategy oneOf) | schema | Each strategy with a valid config. | Missing or zero `rounds`; EMOM carrying `rounds`; non-positive amrap duration. | RESOLVED |
| WK-05 | `resultCapture` exists only on scored strategies and is fixed per strategy: amrap → `scoreType: "rounds_and_reps"`, emom → `"intervals"`, complex → `"cycles"`; `mode` is always `"scored"`; `childDetail` is `none`, `optional`, or `required`. Sequence containers carry no `resultCapture`. | spec §3 Result Capture (supporting: workouts schema capture oneOfs) | schema | AMRAP with `rounds_and_reps` + `childDetail: "optional"`. | AMRAP declaring `intervals`; sequence carrying `resultCapture` (schema rejects). | RESOLVED |
| WK-06 | `rounds_and_reps` is valid only when the container resolves to a deterministic ordered sequence of repetition-based leaf exercises (invariant 25). | spec §3 AMRAP, §8 inv 25 | sem | AMRAP over three rep-based leaves. | AMRAP containing a duration-only child or a nested non-deterministic container: semantic failure. Fixture: `workouts.scenario.json` (`cindy`). | RESOLVED |
| WK-07 | A complex score belongs to the container; `childDetail: "none"` makes the score authoritative and forbids component exercise results (Req 10.10, 10.13). A kettlebell complex needs no synthetic per-movement exercises (Req 10.17). | Req 10.10, 10.17 (supporting: spec §3 Complex) | sem | Complex with one container score and zero child results. | Any exercise result under a `childDetail: "none"` container path. | RESOLVED |
| WK-08 | The container's optional `name` is a direct non-empty display field; the optional `benchmark` object holds named benchmark metadata with required non-empty `name` and optional non-empty `organization`, no other keys. Both are display data only; applications execute the container tree and never infer work from benchmark text. | spec §3 Container Node, Benchmark Metadata | sem (supporting: schema) | Cindy AMRAP container: direct `"name": "Cindy"` plus nested `"benchmark": { "name": "Cindy", "organization": "CrossFit" }`. | `"organization"` as a direct container field instead of inside `benchmark`; `benchmark` missing `name`, with an empty `name`, or with extra keys (schema rejects); work derived from benchmark text. | RESOLVED |
| WK-09 | An exercise node has `id`, `exerciseId` (retained reference), required `stimulus` (`strength`, `hypertrophy`, `power`, `conditioning`, `mobility`), optional `setType` (`warmup`, `working`), required `prescription`, optional `notes`. Exercise nodes never configure result capture; the parent container owns it. | spec §3 Exercise Node (supporting: workouts schema; Req 10.11 context) | schema (supporting: sem, inv 2) | Full node as in spec examples. | Unknown stimulus; `resultCapture` on an exercise node (schema rejects). | RESOLVED |

## 3. Prescription rules

| ID | Contract | Source | Owner | Positive case | Negative case | Status |
| --- | --- | --- | --- | --- | --- | --- |
| WK-10 | A prescription uses only dimensions supported by the referenced exercise with compatible units; `reps` is a plain non-negative integer in prescriptions and results (invariants 7, 8). | spec §3 Prescription, §8 inv 7-8 (supporting: workouts schema) | sem | `{ "reps": 5, "weight": { "value": 225, "unit": "lb" } }` on a squat. | `weight` on an exercise without a weight dimension; `{"value":1,"unit":"mi"}` for weight. | RESOLVED |
| WK-11 | Reps targets are one of: exact integer ≥ 0; `{target, qualifier: "approximate"}`; inclusive range `{min, max}` (both ≥ 0). Actual repetition results are always non-negative integers. | spec §3 Prescription (supporting: workouts schema `repsPrescription`) | schema | All three forms validate. | Open ranges, negative bounds, unknown qualifiers. | RESOLVED |
| WK-12 | `effort` targets are `{type: "failure"}`, `{type: "rir", target ≥ 0}`, or `{type: "rpe", target 1..10}`. Effort is not a measurement dimension and never appears in `values`. | spec §3 Effort Targets (supporting: workouts schema `effortTarget`; results schema `resultValues`) | schema (supporting: sem) | All three targets. | `effort` inside result `values`; rpe 0 or 11. | RESOLVED |
| WK-13 | `loadStrategy` types are `fixed`, `ascending`, `descending`, `self_selected`; the optional fields are `firstIteration` (constant `maximal_for_prescription`) and `adjustment` (constant `decrease_to_repeat_effort`). It applies across iterations of the nearest repeated container. | spec §3 Load Strategies (supporting: workouts schema `loadStrategy`) | schema (supporting: sem resolver, Phase 48) | Descending strategy in a 3-round container. | Unknown type or free-text adjustment. | RESOLVED |
| WK-14 | Top-level prescription fields are defaults for every iteration. An `iterations` entry overrides only the fields it contains; omitted fields inherit top-level values; an entry may add a field with no top-level default; `null` cannot remove an inherited field (invariant 27; Req 10.2-10.3). | Req 10.2-10.3 (supporting: spec §3 Iteration-Specific Prescriptions; workouts schema `prescription`; Arch ADR-021) | sem (resolver, Phase 48) | Spec three-round example: iteration 1 = 5×80 kg, iteration 2 = 3×100 kg, iteration 3 = 8×100 kg. | Expecting array order as precedence; expecting `null` to clear a default. | RESOLVED |
| WK-15 | Each iteration number appears at most once per prescription; duplicates are rejected (invariant 27; Req 10.4). Iteration numbers are one-based; for a finite repeated container an override number cannot exceed the configured count (Req 10.5). | Req 10.4-10.5 (supporting: spec §3; spec §8 inv 27) | sem | One entry per number 1..N. | Two entries with `iteration: 2` (spec's invalid example); `iteration: 4` in a 3-round container; `iteration: 0`. | RESOLVED |

## 4. Prior-production compatibility and curation

| ID | Contract | Source | Owner | Positive case | Negative case | Recovery | Status |
| --- | --- | --- | --- | --- | --- | --- | --- |
| WK-16 | The build downloads the prior production bundle (`https://repjot.com/exercises.json`, `workouts.json`) and fails when a published ID is missing or reused in a different namespace (Req 6.13-6.14). For the first release, gate 7 records the blank-baseline decision instead of downloading prior files. | Req 6.13-6.14 (supporting: Arch §18 gate 7; GATES §2) | compat | First release: blank baseline recorded, no network request. Later release: IDs compared. | Missing or reused ID in a later release: build fails with the exact ID and namespace. | Network failure blocks the release rather than skipping comparison (Arch §18). | RESOLVED |
| WK-17 | The compatibility comparison preserves node type, parent, exercise reference, container strategy, scoring contract, and previously supported measurement units; it does not compare content hashes, labels, instructions, notes, or prescriptions (Req 6.15-6.16). Label/instruction/note/prescription edits keep IDs and apply to historical views (Req 6.2). | Req 6.2, 6.15-6.16 (supporting: versioning §Static bundle compatibility) | compat | Renamed exercise with same ID and units passes. | Removed unit `lb` from a published weight dimension: build fails. | — | RESOLVED |
| WK-18 | The build reports every workout and scored or timed container affected by a newly deprecated exercise (Req 6.7). This report is data for the omission contract (TR-12) and never mutates documents. | Req 6.7 (supporting: spec §1) | compat (supporting: curation) | New deprecation of `push-up` lists Cindy containers. | Silent deprecation without the report. | — | RESOLVED |
| WK-19 | Source exercise data comes from local `free-exercise-db`; a transformation script plus allowlist produces the curated directory; curated values absent from source (laterality, movement pattern, measurements) are defined by curation; source `body only` maps to no equipment; a source `null` value requires equipment curation before publication (Req 13.4-13.5). | Req 13.1-13.5 (supporting: GATES §2 external gates) | curation | `body only` → `equipmentIds: []`. | Publishing an exercise whose source equipment is `null` without a curated value. | Missing human curation approval is unavailable external evidence, not a fixture failure (GATES §2). | RESOLVED |
| WK-20 | Static documents ship in the bundle and are validated by schema plus semantic cross-file checks at build time; an invalid static bundle blocks application load with a blocking error and no workout use. | Req 7.4 (supporting: Arch §9 startup states) | curation build pipeline (supporting: schema, sem, bootstrap) | Valid fixtures load to the anonymous landing page. | Any schema or semantic failure in `exercises.json`/`workouts.json`: app shows blocking error. | Reload after deployment repair. | RESOLVED |
