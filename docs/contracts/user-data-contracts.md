# User data contracts: `preferences.json` and `results-YYYY-MM.json`

Status legend and source abbreviations: see `docs/contracts/README.md`. Owner abbreviations: sem = semantic validator, merge-r / merge-p = result / preference merge modules, sync = sync coordinator, session = session service, facade = application facades (the caller/save-coordinator layer owning the per-`(accountKey, logicalName)` local save queue), schema = JSON Schema gate. The first owner listed is primary; gates after `supporting:` are auxiliary and never co-own the rule.

## 3. Tombstones and sync copies

| ID | Contract | Source | Owner | Positive case | Negative case | Status |
| --- | --- | --- | --- | --- | --- | --- |
| RS-15 | Deleting a session removes it from `sessions` and adds a permanent tombstone `{sessionId, deletedAtUtc}` to the original shard. Tombstones are never auto-removed (a stale device could restore the session); Delete All User Data physically deletes shards (invariant 20). | Req 11.14 (supporting: spec §5 Session Tombstone; storage §Writes and conflicts) | merge-r (supporting: session; sem document-exclusivity check, Phase 5) | Delete then sync on three devices: no device restores the session. | A live session and a tombstone sharing an ID in one merged document (inv 20); automatic tombstone pruning. | RESOLVED |
| RS-16 | During synchronization, tombstones are applied before live-session merge; a tombstone wins over a stale live session with the same ID and never creates a sync copy (invariant 21; ownership: Phase 37 per GATES §2). | spec §8 inv 21 (supporting: Arch §11 Result merge policy; Req 4.8 context) | merge-r | Tombstone on one side, stale live session on the other: session gone, no fork. | A tombstone-versus-live conflict producing a sync copy. | RESOLVED |
| RS-17 | If both sides changed the same live session differently: the remote version keeps the original ID; the pending local version becomes a sync copy with a new reserved `session-` UUID, `conflictOfSessionId` set to the original ID, and preserved status and timestamps (invariant 22; Req 4.8, 11.23). The reserved UUID is persisted in the pending edit before upload and reused on every retry, so one conflict yields at most one copy (Req 11.22-11.24). History labels it `Sync copy`. | Req 4.8, 11.23-11.24 (supporting: Arch §11 Result merge policy + Convergence; spec §5 Session Sync Copy) | merge-r (supporting: sem document-link check, Phase 5; sync, Phase 39/42) | Two clients edit one session: original + labeled fork converge; retry after ambiguity reuses the same UUID. | A second copy for the same conflict key; a fork with moved status/timestamps; a `conflictOfSessionId` pointing at an absent ID in the shard (inv 22). | RESOLVED |

## 4. Invariants 1-28 ownership summary

Invariants 1-6, 7-9 are reference/compatibility rules owned by the semantic validator (Phases 4-5) with fixtures from `tests/fixtures/contract-acceptance/`. Invariant 10-13: score service and semantic validator (Phase 53). Invariants 14-16: result uniqueness and session shape (Phase 5). Invariants 17-18: schema plus lifecycle validation (Phases 5, 54). Invariant 19: shard agreement (Phase 5). Invariant 20: document exclusivity (Phase 5) and merge behavior (Phases 37/46). Invariant 21: tombstone precedence — owned by Phase 37 per GATES §2. Invariant 22: document-link integrity (Phase 5) and sync-copy generation (Phase 39). Invariants 23-24: compatibility gate and semantic resolver (Phases 9, 5). Invariant 25: `rounds_and_reps` determinism (Phase 6/53). Invariant 26: UTC timestamp form — schema plus format assertion (Phase 12/4). Invariant 27: iteration inheritance and uniqueness (Phase 48). Invariant 28: deprecated-omission detail-only containers (Phases 49, 53; terminal-session behavior per approved D-01 Option A).
